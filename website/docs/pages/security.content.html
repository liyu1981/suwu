Access Levels

Suwu automatically detects where you're connecting from and applies the right level of access:

  • Localhost — open https://127.0.0.1:8181 after onboarding.
  • LAN — accessible from your local network with the required onboarding password.
  • Internet — behind a reverse proxy. HTTPS and strong auth required.

Password Authentication

Onboarding requires a password. You can choose one or have Suwu generate a secure password for you:

suwu onboard
# The password is highlighted in the final summary.
# AUTH_PASS stores only its SHA-256 hash.

The web UI prompts for the onboarding password on first access. A device then signs in once and stays signed in: the credential lives in a secure cookie and renews itself on use.

Devices and Sessions

Every device gets its own login session, so a phone and a desktop no longer share — or evict — one credential. A session stays valid for 24 hours of *inactivity*: the window slides on every request, so a device you are using never expires, while one you left alone stops working within a day. A month is the absolute limit, after which the device signs in again.

System Settings → Account → Devices lists them, with the last time each was seen and a revoke button. Revoking one leaves the others working, which is how you sign out a lost phone without changing the password. The same list is available in a terminal:

suwu auth ls            # id, device, last seen, expiry, (this session)
suwu auth rm aaaa1111bbbb
suwu auth rm --all      # sign out every other device

suwu auth talks to the server over its Unix socket, so it needs no password — it is the way back in when a device is locked out. Changing the password signs every device out.

Per-Run Tokens

For temporary access, Suwu also generates a per-run token, displayed in the terminal when the server starts. It works until its own five-minute window closes, and the first device that renews with it is upgraded to a normal session. Share the password, not the token, when someone needs lasting access.

$ suwu serve
  ┌──────────────────────────────────────┐
  │  Suwu is running                     │
  │  https://127.0.0.1:8181              │
  │  Token: abc123xyz                    │
  └──────────────────────────────────────┘
Note

Per-run tokens are displayed once at startup. If you miss it, restart the server to generate a new one.

HTTPS with One Command

Suwu can generate a self-signed certificate and enable HTTPS in one step:

# Generate certs and configure HTTPS
suwu gencerts

# The cert paths are written to ~/.config/suwu/.env
# Restart the server to pick them up
suwu serve

For production use, provide your own certificates:

TLS_CERT_FILE=/path/to/cert.pem \
TLS_KEY_FILE=/path/to/key.pem \
suwu serve

Reverse Proxy Setup

For internet access, put Suwu behind a reverse proxy (nginx, Caddy, etc.). The key headers to forward:

# nginx example
location / {
    proxy_pass http://127.0.0.1:8180;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}

Environment Variables

Variable Description
SERVER_MODE https, http, or https+http (default: https)
HTTPS_PORT / HTTP_PORT Listener ports (defaults: 8181 / 8180)
HOST Bind address (127.0.0.1 default, 0.0.0.0 for all interfaces)
EXTRA_HOSTS Additional allowed hosts, e.g. example.com,*.lan.example
AUTH_PASS SHA-256 hash of the required web password; set by suwu onboard
TLS_CERT_FILE Path to TLS certificate
TLS_KEY_FILE Path to TLS private key
Tip

Browser-visible hostnames (localhost, LAN IP, machine hostname) are always accepted without extra configuration. You only need to set up certificates and reverse proxies for public internet access.
