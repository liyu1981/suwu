# WebGPU Background Externalization — Plan

Status: **implemented** (see the deviation notes below)
Owner area: `frontend/src/components/background/`, `pkg/background/`,
`pkg/wgsl/`, `pkg/server/`, `cmd/Suwu/background.go`, `backgrounds/` (builtin),
`examples/background/` (external examples), `frontend/scripts/wgsl-compiler/`
Related: `docs/EXTENSION_API_PLAN.md` (the data-dir + static-serving precedent),
`frontend/src/components/background/README.md` (current background contract),
`apple-design` (no UI change here), `suwu-tile-plugin-design` (§12 strings).

> **Implementation deviations**
>
> - The compiler bundle (`pkg/wgsl/resolver.js`, 78 KiB minified) and the
>   embedded stdlib (`pkg/wgsl/wgsl-stdlib.json`) are generated by
>   `frontend/scripts/wgsl-compiler/build.mjs` and **committed**; regenerate
>   with `pnpm --dir frontend wgsl:compiler` after a vgpu upgrade. Parity with
>   Node's `resolveShader` output is byte-exact (verified for every entry
>   shader), so §5.3's `AUTO-GENERATED` banner was dropped to keep artifacts
>   identical to the resolver's own output.
> - `.shader.js` freshness has no automatic CI gate: `bg:check` validates that
>   every entry `.wgsl` has a well-formed artifact, and the sources themselves
>   compile via `vgpu check`. Re-run `suwu background build` after editing a
>   `.wgsl`. (A content-hash banner was considered and skipped as over-strict.)
> - Shipping `examples/background/` in the release tarball (open question §14)
>   was resolved as **repo-only**, mirroring `examples/extensions/`.
> - Param formatting uses `decimals` + `suffix` exactly as sketched; the
>   settings UI synthesizes the `format` callback in `external.ts`.

## 1. Goal & scope

Move the **WebGPU shadertoy backgrounds** out of the compiled binary and into
the Suwu data dir, so a background can be added or edited without rebuilding the
Go binary. The frontend fetches each background's implementation from the
backend and executes it.

**One WebGPU background stays built in: `seascape`** (the ocean/wave Shadertoy —
referred to as "oceanscape" in the request). It is authored in the **exact same
directory structure and module ABI** as the external ones and is embedded in the
Go binary, then served through the **same routes**; only its storage differs.
This guarantees the WebGPU family always has at least one background with no
dependency on the data dir or on the list API succeeding.

External (examples, user-installed):

- `atmospheric-landscape`, `cosmos-in-crystal`, `interactive-fluid`,
  `matrix-rain`, `rainforest` — authored under `examples/background/webgpu/`
  (mirroring `examples/extensions/`) and copied by the user into
  `~/.suwu/background/webgpu/`.
- A new server package + routes to list and serve them from
  `~/.suwu/background/webgpu/<id>/`.
- A frontend loader that registers and runs them through the existing registry
  and `startBackground()` path.

Built in (embedded, same structure):

- `seascape` — lives at `backgrounds/webgpu/seascape/`, embedded in the Go
  binary and served at `/backgrounds/webgpu/seascape/…` like any other. A copy
  in the data dir overrides the embedded one, so users can still customize it.

Out of scope (stays embedded in the binary):

- The shared engine `webgpu-render-engine/` — it is the runtime host, not a
  background, and modules consume it through an injected API.
- The CPU backgrounds `ambient-blob` (default) and `video`.

The default background remains `ambient-blob`, so a fresh install renders
something before any background is seeded, and `seascape` is available
immediately for the WebGPU family.

## 2. Current architecture

| Concern | Where |
| --- | --- |
| Registry (id → definition) | `background/registry.ts` (`registerBackground` / `getBackground` / `listBackgrounds`) |
| Definition / param schema | `background/types.ts` (`BackgroundDefinition`, `BackgroundParam`, `gpu`/`cpu` lazy starters) |
| Start chain + fallback | `background/select.ts` → `useBackground.ts` → `BackgroundCanvas.tsx` / `BackgroundPreview.tsx` |
| Shared engine | `background/webgpu/webgpu-render-engine/` (`fragmentScene`, `startGpuBackground`, `storageAsset`, `texture3dAsset`) |
| Background family | `background/webgpu/index.ts` side-effect imports each `shadertoys/<id>/setup.ts` |
| A shadertoy | `setup.ts` (metadata + `start`) + `shaders/*.wgsl` |
| Shader loading | Vite `@vgpu/wgsl/loader-vite` resolves `import` graphs into a `ShaderSource` artifact `{ version: 1, wgsl, functionExports }`; `import('./x.wgsl')` yields `{ default: artifact }` |
| Data dir | `~/.suwu` (`SUWU_VAR` override), `server.New(..., dataDir)` |
| Data-dir precedent | `pkg/extension` (`Dir` / `List` / `Resolve` / `StaticPath` + `ensureWithin`), `/api/extensions` (auth) + `/gqjs/static/…` (unauth static) |
| Embedded web assets | Vite builds into `pkg/assets/web`, `pkg/assets/assets.go` `//go:embed web` |
| Packaging | `.github/workflows/release.yml` (binary + LICENSE), `install.sh` + `suwu onboard` |

A shadertoy's runtime shape is small: **metadata** (id, label, engine, credit,
params) + a **`start(ctx, params)`** function that builds a scene from the
engine and returns a `BackgroundHandle`. Five shadertoys are declarative
(`fragmentScene` + WGSL); `interactive-fluid` is a hand-written `GpuScene` that
also uses `vgpu` primitives (`compute`, `effect`, `pingPongStorage`, `storage`).
The built-in `seascape` is declarative too.

## 3. Constraints that shape the design

1. **CSP forbids executing source strings.** The shell sends
   `script-src 'self'` (`pkg/server/server.go` `csp`). `eval`, `new Function`,
   and `blob:` module scripts are blocked. We therefore cannot take JS text from
   an API response and execute it; we must serve it as a **same-origin module
   URL** and load it with `import(/* @vite-ignore */ url)`.
2. **ES module imports cannot carry an `Authorization` header.** Auth is a
   Bearer header or `?token=` query (`pkg/auth` `ValidateAPIRequest`), and a
   module's relative imports do not inherit a query token. The background
   **static** route must therefore be unauthenticated (like `/gqjs/static/…`);
   the **listing** route stays authenticated.
3. **WGSL `import` graphs exist.** Shaders import relative files
   (`./fluid-common.wgsl`, `./common.wgsl`) and the stdlib
   (`@vgpu/wgsl-std/hash`). The runtime resolver `@vgpu/wgsl/runtime` imports
   `node:fs` and is **Node-only**, so the browser cannot resolve raw `.wgsl`
   graphs. Shaders must be **precompiled** to self-contained `ShaderSource`
   artifacts before they reach the browser.
4. **`fragmentScene` / `effect` consume `ShaderSource`, not raw strings.**
   A fetched `.wgsl` text is not directly usable; it must be wrapped as
   `{ version: 1, wgsl, functionExports: [] }` and import-resolved.
5. **Params are functions today.** `BackgroundNumberParam.format` and
   `BackgroundFileListParam.store/list/clear` are functions and cannot be JSON.
   WebGPU shadertoys only use `number`/`select`/`boolean`/`color`/`text`, so a
   JSON-safe param schema covers them (drop `format` in favour of `decimals` +
   `suffix`; `fileList` is not used by WebGPU backgrounds).

## 4. Design overview (chosen)

A background is a **directory** in the data dir:

```
~/.suwu/background/webgpu/<id>/
  background.json            # JSON-safe metadata + params
  scene.js                   # ESM: export default function create(api) { … }
  shaders/
    <name>.wgsl              # authored source (reference / editing)
    <name>.shader.js         # generated ShaderSource artifact (committed)
```

- **`background.json`** is read eagerly to build the registry list (no code
  execution) — the System Settings selector, the preview and the canvas can all
  resolve ids and params before `scene.js` runs.
- **`scene.js`** is imported lazily, only when the background actually starts.
  It is a plain ESM module that exports a factory `create(api)` and returns
  `{ start(ctx, params) }`. It imports its **precompiled** shader artifacts with
  ordinary relative ESM imports (`import cosmos from './shaders/cosmos.shader.js'`),
  which the browser resolves natively.
- **The engine and `vgpu` are injected**, never imported by `scene.js`:
  `api = { ...engineModule, vgpu }`. This keeps `scene.js` free of bare
  specifiers the browser cannot resolve, and pins the engine version to the
  running frontend.
- **Server** mirrors `pkg/extension`: an authenticated `/api/backgrounds` list
  and an unauthenticated `/backgrounds/webgpu/<id>/<path>` static route with a
  file-type allow-list, path containment and `nosniff`.
- **Built-in `seascape`** is embedded in the Go binary and resolved through the
  *same* server code path: **disk first, embedded fallback**. The frontend can
  not tell it apart from an external background, and a data-dir copy overrides
  it. The alternative — bundling `seascape` into the Vite frontend bundle and
  registering it eagerly — was rejected because it would give the built-in a
  different load path and a different authoring location from the external
  ones; the request is explicitly that the built-in "follow the same structure".
- **Frontend** hydrates the registry from a localStorage cache (instant, no
  flash), then revalidates against `/api/backgrounds` and bumps a revision atom.

Alternatives considered:

- **Data-only descriptor** (JSON scene graph + WGSL, interpreted by the engine):
  safe and no code execution, but cannot express `interactive-fluid`'s custom
  solver/pointer input or the asset builders (glyph atlas, noise volume). Would
  need a second, JS escape hatch anyway.
- **Blob/`eval` execution of fetched source**: blocked by CSP; adding `blob:`
  to `script-src` materially weakens the policy. Rejected.
- **Browser-side WGSL resolver**: `@vgpu/wgsl/runtime` is Node-only. Rejected.

## 5. Directory & manifest format

### 5.1 `background.json`

```json
{
  "id": "cosmos-in-crystal",
  "label": "Cosmos in Crystal",
  "engine": "webgpu-render-engine",
  "credit": {
    "author": "nayk",
    "url": "https://www.shadertoy.com/view/MXccR4"
  },
  "params": [
    {
      "kind": "number",
      "key": "speed",
      "label": "Animation speed",
      "hint": "Scales the tunnel drift and the colour churn. 0 freezes the scene.",
      "default": 1,
      "min": 0,
      "max": 3,
      "step": 0.05,
      "decimals": 2,
      "suffix": "×"
    },
    {
      "kind": "select",
      "key": "detail",
      "label": "Detail",
      "hint": "Higher detail renders more scene pixels — sharper, but heavier.",
      "default": "high",
      "options": [
        { "value": "low", "label": "Low (0.5 MP)" },
        { "value": "medium", "label": "Medium (1 MP)" },
        { "value": "high", "label": "High (2 MP)" },
        { "value": "ultra", "label": "Ultra (4 MP)" },
        { "value": "native", "label": "Native (canvas)" }
      ]
    }
  ]
}
```

- `id` must equal the directory name (validated server-side and by the check
  script).
- `engine` is `"webgpu-render-engine"` for all six.
- Param kinds allowed externally: `number` (with optional `decimals`/`suffix`
  instead of the `format` function), `boolean`, `select`, `text`, `color`.
  `fileList` is rejected (it needs JS callbacks and is CPU-video-only).
- The loader turns `decimals`/`suffix` into the same `format` function the
  existing `BackgroundNumberParam` expects, so `types.ts` and the settings UI
  are unchanged.

### 5.2 `scene.js` — module ABI

```js
// cosmos-in-crystal/scene.js
import cosmosShader from './shaders/cosmos.shader.js';
import blitShader from './shaders/blit.shader.js';

const DETAIL_BUDGETS = { low: 0.5, medium: 1, high: 2, ultra: 4, native: Infinity };

export default function create({ fragmentScene, startGpuBackground }) {
  async function start(ctx, params) {
    const speed = typeof params?.speed === 'number' ? params.speed : 1;
    const megapixels = DETAIL_BUDGETS[params?.detail] ?? 2;
    return startGpuBackground(
      'cosmos-in-crystal',
      fragmentScene({
        label: 'cosmos-in-crystal',
        targets: { scene: { format: 'rgba8unorm', clearColor: [0, 0, 0, 1], budget: megapixels } },
        reducedMotionSettle: 1,
        passes: [
          { shader: cosmosShader, target: 'scene',
            bindings: ({ size, time }) => ({ params: { resolution: size, time: time * speed, _pad: 0 } }) },
          { shader: blitShader, target: 'canvas',
            bindings: ({ targets, sampler }) => ({ src: targets.scene, samp: sampler }) },
        ],
      }),
      ctx,
      params,
      { clearColor: [0, 0, 0, 1] },
    );
  }
  return { start };
}
```

- The default export is the factory; `create` is accepted as a named fallback.
- `interactive-fluid` additionally uses `api.vgpu.{compute, effect, frame,
  pingPongStorage, storage}` instead of `import … from 'vgpu'`.
- Shader artifacts are imported with **relative ESM** (`./shaders/x.shader.js`);
  no `loadShader` helper is needed.

### 5.3 Shader artifacts (`*.shader.js`)

Generated, committed, and validated by CI (shape + `vgpu check` on the source).
Byte-identical to the resolver's own output — no banner comment:

```js
export default {
  version: 1,
  wgsl: '…resolved, import-free WGSL…',
  functionExports: [],
};
```

### 5.4 Compiling WGSL → `*.shader.js`

The runtime cannot resolve WGSL import graphs (§3.3), so every **entry**
`.wgsl` (a file with `@fragment`/`@compute`) is precompiled to a sibling
`<name>.shader.js`. The compiler is **embedded in the `suwu` binary** and
surfaced as one command:

```bash
suwu background build shaders/cosmos.wgsl > shaders/cosmos.shader.js
```

- `suwu background build <file.wgsl>` reads the entry, resolves its import graph
  (relative `./*.wgsl` and `@vgpu/wgsl-std/*`), and writes the compiled module
  to **stdout**:
  `export default { version: 1, wgsl: "…import-free WGSL…", functionExports: [] };`
- Diagnostics go to **stderr** with a non-zero exit; stdout is written only on
  success, so `>` is safe.
- This is the **only** compiler surface. No on-demand server compilation, no
  directory build, no browser-side resolver (§15).
- No Node/vgpu toolchain is required at runtime: the resolver JS is bundled and
  embedded, running on the QuickJS engine the binary already ships (`pkg/gqjs`,
  `qjs`/`wazero`).
- Only entry files need compiling; helper modules (e.g. `fluid-common.wgsl`) are
  inlined transitively. An entry with no imports is wrapped verbatim.
- Artifacts are **committed**, so `go build` and the release never run the
  compiler. Editing a `.wgsl` means re-running the command and redirecting to
  the `.shader.js`.
- A repo/CI freshness check can compare each committed `.shader.js` against a
  freshly compiled one (via the built `suwu` binary, or the Node
  `transformWgsl` path kept as CI-only tooling).

## 6. Server side

### 6.1 `pkg/background/background.go` (new, mirrors `pkg/extension`)

```go
const DirName = "webgpu"                 // ~/.suwu/background/webgpu
const ManifestFile = "background.json"
const EntryFile = "scene.js"

// Builtin is the embedded fallback tree, exposed by the top-level
// `backgrounds` Go package (see §8.1). It currently holds only `seascape`.
func Dir(dataDir string) string          // filepath.Join(dataDir, "background", DirName)
func ValidID(id string) bool             // same idRe as extensions
func List(dir string) ([]Manifest, error)                 // disk entries, sorted
func ListEmbedded(fsys fs.FS) ([]Manifest, error)         // embedded entries, sorted
func Resolve(dir, id string) (Manifest, error)            // reads+validates background.json
func StaticPath(dir, id, rel string) (string, error)      // containment + symlink defense
```

- Reuse the extension package's containment/`ensureWithin` approach (copy it;
  do not export extension internals). The manifest struct validates `id`,
  `engine`, `params` kinds, and that `scene.js` exists.
- **Resolution order is disk first, embedded fallback.** `List` unions disk and
  embedded by id (disk overrides), `Resolve` prefers disk, and the static route
  opens the disk file first, then the embedded one. `seascape` therefore
  behaves exactly like an external background, and copying it into the data dir
  overrides the built-in.
- `SUWU_BACKGROUNDS_DIR` env (or a `--backgrounds-dir` flag) overrides `Dir`
  for development so the repo tree can be served directly.

### 6.2 Routes (`pkg/server`)

| Route | Auth | Purpose |
| --- | --- | --- |
| `GET /api/backgrounds` | yes (Bearer/query) | `{ "backgrounds": [ Manifest, … ] }` for the registry (disk ∪ embedded) |
| `GET /backgrounds/webgpu/<id>/<path>` | no | serve `scene.js`, `*.shader.js`, `*.wgsl`, `*.json` (disk, then embedded) |

- The static route mirrors `pkg/server/extension_static.go`: an extension
  allow-list (`.js`, `.mjs`, `.wgsl`, `.json`), `X-Content-Type-Options:
  nosniff`, per-file size cap (8 MiB), and `404` for anything else.
- `seascape` is served from the embedded FS through the **same** handler; the
  frontend never special-cases it.
- `grantOpaqueOriginCORS` is **not** needed (the app is same-origin); same-origin
  module fetches carry cookies, but we do not rely on them here.
- The manifest is also served statically (harmless, already public via the
  module dir); the authenticated list is what the UI consumes.
- No CSP change is required: `script-src 'self'` allows the same-origin module
  import, and `connect-src 'self'` allows the module's shader/asset fetches.

### 6.3 Server tests

Mirror `pkg/extension/*_test.go` and `pkg/server/extension_static_test.go`:
`List`/`Resolve` happy paths, invalid id, missing manifest/entry, param
validation, `StaticPath` traversal + symlink escape, route 404s on unknown
types, and the authenticated list.

## 7. Frontend side

### 7.1 Registry stays synchronous; a revision atom drives re-render

`getBackground` / `listBackgrounds` keep their synchronous Map API. External
definitions are registered into it as they load. The embedded `seascape` is
**not** a special case: the server includes it in the same `/api/backgrounds`
list and serves its module from the same route, so there is exactly one
registration path.

```ts
// store/settings.ts (or background/external.ts)
export const backgroundsRevisionAtom = atom(0);
```

- `SettingsView` (which calls `listBackgrounds()` during render) and
  `BackgroundCanvas` / `BackgroundPreview` subscribe to the revision atom so
  they re-resolve after the list arrives.

### 7.2 `background/external.ts` (new)

```ts
const CACHE_KEY = 'suwu:external-backgrounds';
const LIST_URL = '/api/backgrounds';
const BASE = '/backgrounds/webgpu/';

export function hydrateExternalBackgrounds(): void  // sync from localStorage cache
export async function loadExternalBackgrounds(): Promise<void> // fetch + register + cache + bump

function registerFromManifest(m: ExternalManifest): void {
  registerBackground({
    id: m.id, label: m.label, engine: m.engine, credit: m.credit,
    params: m.params.map(toParam),          // decimals/suffix -> format()
    gpu: () => loadExternalScene(m.id),
  });
}

async function loadExternalScene(id: string): Promise<BackgroundModule> {
  const [engine, vgpu] = await Promise.all([
    import('./webgpu/webgpu-render-engine'),
    import('vgpu'),
  ]);
  const mod = await import(/* @vite-ignore */ `${BASE}${id}/scene.js`);
  const create = mod.default ?? mod.create;
  return await create({ ...engine, vgpu });
}
```

- `main.tsx` (or `AppShell`) calls `hydrateExternalBackgrounds()` synchronously
  before render, then `loadExternalBackgrounds()` after mount.
- The localStorage cache makes a repeat load resolve the stored id with **no
  flash**; revalidation then re-registers (idempotent `Map.set`) and bumps the
  revision.
- Failure is non-fatal: log a warning, keep the cached/embedded set, leave the
  default background working.

### 7.3 Remove the eager family imports

- Delete `background/webgpu/index.ts`'s side-effect imports (or the file) and
  drop `import './webgpu'` from `background/index.ts`.
- Keep `webgpu-render-engine/` where it is; it is now only reached through the
  external loader's dynamic import.
- `types.ts`: add an optional `external?: true` / `sourceUrl?: string` on
  `BackgroundDefinition` if the UI wants to mark user-provided backgrounds
  (optional).

## 8. Packaging, seeding & dev workflow

### 8.1 Canonical source in the repo

The built-in lives at `backgrounds/webgpu/seascape/`; the external backgrounds
are **examples** under `examples/background/webgpu/`, mirroring
`examples/extensions/`. Both use the identical directory format and are compiled
by the same script.

```
backgrounds/
  embed.go                       # package backgrounds; //go:embed webgpu/seascape
  webgpu/
    seascape/                    # BUILT IN (embedded in the Go binary)
      background.json
      scene.js
      shaders/seascape.wgsl
      shaders/seascape.shader.js
      shaders/blit.wgsl
      shaders/blit.shader.js

examples/
  backgrounds/
    README.md                    # "copy a dir into ~/.suwu/background/webgpu/"
    webgpu/
      cosmos-in-crystal/         # external example
        background.json
        scene.js
        shaders/cosmos.wgsl
        shaders/cosmos.shader.js
        shaders/blit.wgsl
        shaders/blit.shader.js
      atmospheric-landscape/ interactive-fluid/ matrix-rain/ rainforest/
```

- `backgrounds/embed.go` is a tiny Go package so `//go:embed` can embed the
  built-in tree without copying it into another package:

  ```go
  package backgrounds

  import "embed"

  //go:embed webgpu/seascape
  var Builtin embed.FS
  ```

  `pkg/background` consumes `backgrounds.Builtin` for the disk-first/embedded
  fallback (§6.1). Only `seascape` is embedded — the examples live outside the
  pattern.
- `scene.js` is plain ESM (no TS) so it is directly importable in the browser.
  It is **not** part of the Vite bundle.
- Conversion of the six `setup.ts` files is mechanical: move params into
  `background.json`, replace the engine import with the injected `api`, and
  change `import shader from './shaders/x.wgsl'` to `'./shaders/x.shader.js'`.
  `interactive-fluid` also swaps `import … from 'vgpu'` for `api.vgpu.*`.
- `examples/background/README.md` documents the copy step, exactly like
  `examples/extensions/README.md`. A future `suwu background add <id>` can copy
  from a bundled examples dir (open question §14).

### 8.2 Release + install

- Examples are **not** auto-seeded: like `examples/extensions/`, the user copies
  a dir into `~/.suwu/background/webgpu/` (documented in
  `examples/background/README.md`).
- The built-in `seascape` is embedded, so a binary-only install always has one
  WebGPU background plus `ambient-blob`; no release tarball change is strictly
  required for it.
- `release.yml` **optionally** adds `examples/background` to the archive so a
  future `suwu background add` can seed from it (open question §14). If shipped,
  `install.sh`/`onboard` copy the five examples **only if missing**.
- `cmd/Suwu/onboard.go`: no background seeding by default; if the examples are
  shipped, add the same idempotent "copy if missing" step.

### 8.3 Development

- `SUWU_BACKGROUNDS_DIR=./examples/background/webgpu suwu serve` serves an
  example tree directly (no copy); pointing it at `backgrounds/webgpu` lets the
  repo `seascape` override the embedded copy via disk-first resolution.
- After editing a `.wgsl`, regenerate its artifact with the embedded compiler:
  `suwu background build shaders/x.wgsl > shaders/x.shader.js`; then reload the
  browser to pick up `scene.js`/shader changes (module cache busted by a `?v=`
  query in dev, or a hard reload).

## 9. Security

- External background code runs in the **app origin with full privileges**
  (unlike extensions, which run in a sandboxed iframe). There is no practical
  sandbox that also grants WebGPU + the main canvas, so this is accepted:
  backgrounds are **trusted local user code**, like a shell profile.
- Rules to document in the README and the manifest:
  - Backgrounds are loaded **only** from the local data dir; never a remote URL.
  - The static route is unauthenticated — **never put secrets** in a background
    dir.
  - The route is same-origin only, allow-listed by extension, size-capped, and
    path-contained (with symlink defense).
- CSP is unchanged. A future hardening option (out of scope) is a module Worker
  + `OffscreenCanvas` sandbox, at the cost of reworking the engine's DOM/canvas
  access.

## 10. Migration & compatibility

- Stored `backgroundAtom` ids for external backgrounds resolve once the list
  loads (cached list → no flash). A removed background falls back to
  `ambient-blob` via the existing `resolveBackgroundId`.
- Stored `backgroundParamsAtom` overrides are keyed by id and validated against
  the manifest schema by `resolveBackgroundParams` — unchanged.
- The frontend's `types.ts` / `select.ts` / `params.ts` / settings UI need no
  structural change beyond the revision atom and the param `format` synthesis.
- No server data migration: the directory simply starts empty; seeding is
  idempotent.

## 11. Edge cases & risks

- **First-run**: the built-in `seascape` is always present from the embedded FS,
  so the WebGPU family is never empty; `ambient-blob` remains the default.
  External backgrounds appear only after seeding. Surface a hint in System
  Settings when only the built-in is present (optional).
- **Built-in override**: a data-dir `seascape` shadows the embedded one
  (disk-first). If it is invalid, `Resolve` must fall back to the embedded copy
  rather than dropping the built-in.
- **Manifest/schema drift**: a hand-edited `background.json` is validated
  server-side (list omits invalid entries) and re-validated client-side; a bad
  entry is skipped, never crashes the shell.
- **Shader artifact staleness**: the check script compares mtimes/hashes; CI
  fails on a `.wgsl` without a regenerated `.shader.js`.
- **Module caching in dev**: Vite/browser may cache `scene.js`; use a cache-bust
  query in dev or document a hard reload.
- **`import.meta.url` base**: relative shader imports resolve against the module
  URL, so the route must serve the directory with correct relative paths
  (trailing-slash handling, no redirect that drops the path). The embedded FS
  must present the same relative layout as the disk dir.
- **CSP**: verified no change needed; if a background ever needs `blob:` (it
  should not), that is a separate, deliberate policy change.
- **Engine/API version skew**: `scene.js` only ever sees the running frontend's
  engine via `api`, so a newer engine cannot be mismatched with an old module
  beyond the documented API surface.

## 15. Appendix — embedding the WGSL compiler (`suwu background build`)

**Feasible, and cheap: the binary already ships QuickJS.** `pkg/gqjs` embeds
`github.com/fastschema/qjs` (QuickJS) on `wazero` (pure Go, `CGO_ENABLED=0`) and
runs JS for extensions, with `fs`/`process` host bindings. The embedded compiler
reuses that engine; it does not add one.

**Scope is exactly one command, output to stdout:**

```bash
suwu background build <file.wgsl> > <file>.shader.js
```

No on-demand server compilation, no directory build, no browser-side resolver.

### 15.1 What it does

- Reads the entry `.wgsl`, builds an in-memory `path → text` module map for the
  whole import graph (relative files + embedded `@vgpu/wgsl-std`), and calls the
  bundled `resolveShader` with `{ entry, modules, packageMap, validate: false }`.
- Prints the `ShaderSource` module to **stdout**:
  `export default { version: 1, wgsl: "…", functionExports: [] };`
- Diagnostics go to **stderr** with a non-zero exit; stdout is written only on
  success.
- `validate: false` skips the Node/WebGPU validation path (`@vgpu/adapter-node`).

### 15.2 Node builtins to shim

| Builtin | Used by | Shim |
| --- | --- | --- |
| `node:path` | `dirname` (resolve-shader.js), `join`/`normalize`/`isAbsolute`/`extname`/`sep` (package-resolution.js) | small posix path shim |
| `node:crypto` | `createHash` (cache-key.js — **always** called at resolve-shader.js:113) | pure-JS hash shim |
| `node:buffer` | `isUtf8` (shader-graph-files.js, fs path) | trivial shim |
| `node:module` | `createRequire` (package path) | throw stub |
| `node:fs` / `node:fs/promises` | only when `modules`/`packageMap` are absent | throw stub |
| `@vgpu/adapter-node` | dynamic import, GPU validation only | stub; pass `validate: false` |

With `resolveShader({ entry, modules, packageMap, validate: false })` the resolver
**never touches the filesystem**: relative imports go through `defaultVirtual`,
and `@vgpu/wgsl-std/*` is covered by `packageMap` + `modules`. The entry and
every `.wgsl` are supplied as an in-memory `path → text` map; the stdlib
(`@vgpu/wgsl-std/src/**`, 164 KB) is embedded for the package map.

### 15.3 Cost & risk

- Bundle the resolver to one ESM/IIFE with the shims and `//go:embed` it:
  roughly **200–400 KB minified**; embed `@vgpu/wgsl-std/src/**` (164 KB) for the
  package map. QuickJS (`qjs.wasm`, ~1 MB) is already in the binary, so no new
  engine cost.
- New `pkg/wgsl` Go wrapper over `qjs` plus a `cmd/Suwu` `background build`
  subcommand (~1–2 focused days incl. tests), reusing the `pkg/gqjs`
  host-binding pattern.
- Risks:
  - **Shim gaps / an unexpected fs path** — mitigated by the
    `modules` + `packageMap` design; add a parity test that compiles all six
    backgrounds and diffs against the Node `transformWgsl` output.
  - **vgpu version drift** — pin the bundled resolver version and check it.
  - **qjs ES-feature gaps** — low; `qjs` already runs extension code and its own
    tests cover modules, `export default`, and top-level await.
- Performance: one graph resolve is tens of milliseconds; fine for a one-shot
  CLI.

### 15.4 Recommendation

Ship `suwu background build` as the canonical compiler. The committed
`.shader.js` stays the runtime format; the CLI replaces the Node script for
authors and for CI freshness checks. The Node `transformWgsl` path may remain as
CI-only tooling but is not required for users.
